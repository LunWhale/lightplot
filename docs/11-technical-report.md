> **这份文件不是给操作者看的。** 操作者看 `AGENT.md`。

## 1. 架构：为什么 AI 只填 YAML

### 1.1 唯一铁律

```
AI 只填 data/*.yaml  →  代码算所有几何  →  三道门禁复核  →  出图
```

**AI 永远不写坐标、不画线、不算字号。**

### 1.2 这条规则是怎么被逼出来的

早期版本让模型直接生成绘图代码。结果是**每一次修改都在破坏上一次的修复**：

- 加了图例，色片表和图例的宽度算法不一致 → 一个对齐一个不对齐
- 换了字体，字宽变了，白底遮罩盖不住字（遮罩按字号算，字按实际宽度画）
- 挪了一个标签，压住了另一个标签

这是典型的"打地鼠"：**几何和内容耦合在一起，改任何一个参数都要重新解一遍全局布局。**

数据与几何分离之后，问题变成两类，各自可解：
- **内容问题** → 改 YAML，不需要碰代码
- **几何问题** → 改代码，YAML 不动，可以拿同一份数据反复回归

### 1.3 三个不可动摇的推论

**① 几何必须有唯一来源。**
`paper.py`（视觉语法常量）+ `data/rig.yaml`（场地与灯具）= 全部几何输入。
`render.py` 和 `section.py` 都从这里读，不许各自写死数字。

> 反例（已修）：`src/section.py` 的图签字段曾经和 `render.py` 各写一份，
> 改了一边忘了另一边。现在都从 `rig.yaml` 的 `meta` 读。

**② 单位必须在一个地方换算。**
`EM_TO_CAP = 0.7163` 只在 `metrics.py` 定义。`paper.py` 和 `pdfout.py` 都 `import` 它。

> 这次精简之前它有三份副本（`paper.py` / `metrics.py` / `pdfout.py`）。
> 三份副本的漂移是**静默的** —— 只有一处来源会错，而错的那处只影响一类输出。
> 这类问题极难在图上肉眼发现。已合并。

**③ 校验只能有一份。**
`qc.check_rig()` 是唯一的数据校验器。

> 这次精简之前 `render.py` 里还有一份 `validate()`，是 `qc.check_rig()` 的**弱化复制品**：
> 少了 trim 合理性、吊点越界、beam 缺失、position.type 合法性四条检查，
> 还硬编码放过 `pos == "SET EDGE"`（那是 SET EDGE 还不是正式位置时的补丁）。
> 两份校验器必然漂移，而**弱的那份会先放行**。已删除。
>
> 同理删掉了 `qc.check_layout()` —— 它是死代码，真正的重叠检查在
> `verify.py` 里按**真实 bbox** 做，比估算 bbox 强得多。留着只会让人以为
> 排版避让有两条路径。

## 2. 单位：这套系统里最容易错的地方

**如果只记住这一节，记住 §2.1。**

### 2.1 em 与 cap（"字大得离谱"的真根因）

```
pymupdf  page.get_text("dict") → span["size"]  是 em
DXF      TEXT.height                           是 cap
```

同一个字体，`em > cap`。Arial 的实测比值：

```
cap / em = 1467 / 2048 = 0.7163
```

如果用 `span["size"]`（em）直接当 DXF 的 `TEXT.height`（cap）写：

```
实际渲染大小 = 想要的 × (1 / 0.7163) = 1.396 倍
```

**这就是用户说的"雷霆大文字"。不是"字号调大了一点"，是整整 1.4 倍。**

现在的约定：

| 位置 | 单位 | 说明 |
|---|---|---|
| `paper.FS["*"]` | **cap（mm）** | 全表都是 cap，注释里标了原始 em 供核对 |
| DXF `TEXT.height` | cap（mm） | 直接写 `paper.FS` |
| PDF `fontsize` | **em（pt）** | 写之前 `/ EM_TO_CAP * K` |
| `metrics.width_mm()` | 输入 cap | 内部转 em 问字体要 advance width |

**改任何字号之前，先确认你写的是 cap 还是 em。**

### 2.2 图纸 mm 与真实 mm

两个坐标系，两套产物：

| 目录 | 内容尺寸 | 用途 |
|---|---|---|
| `out/*.dxf` | **图纸 mm**（A1 = 841×594） | 复核、黄金图、打印 |
| `out/cad/*.dxf` | **真实 mm**（×25 = 21025×14850） | Vectorworks 导入 |

**为什么必须分成两份：**
`verify.py` 和 `golden.py` 全部按图纸 mm 判断（图框 841、桁架节距 11.77）。
如果就地放大 25 倍，这两道门会全崩 —— 而它们的失败信息会指向"几何错了"，
把你引向完全错误的方向。

> 这是踩过的坑：`to_model_scale()` 曾经在原地改 `out/*.dxf`，
> 结果 `verify.py` 报"图框 21025×14850 应为 841×594"，
> 第一反应是"渲染坏了"，实际是复核基准和产物不匹配。

### 2.3 DXF 的两套"界限"（图只占半页的真根因）

DXF 的 header 里有**两对**界限变量，含义不同：

| 变量 | 空间 | Vectorworks 用它做什么 |
|---|---|---|
| `$LIMMIN` / `$LIMMAX` | **模型空间** | "缩放到界限" |
| `$PLIMMIN` / `$PLIMMAX` | **图纸空间 / layout** | **页面尺寸** |

只改 `$LIMMAX` 不改 `$PLIMMAX`：内容 841 宽、页面 420 宽 →
**图正好占页面的 50%**。用户截图里那个"图只占一半"就是这个。

`841 / 420 = 2.00` —— 这个整数比是关键线索。看到"正好一半/正好两倍"，
先怀疑纸张尺寸，不是内容尺寸。

## 3. 缺陷全表（按子系统）

每条格式：**症状 → 根因 → 修法 → 残留风险**。

### 3.1 几何与绘制

| # | 症状 | 根因 | 修法 | 残留 |
|---|---|---|---|---|
| G1 | 桁架画成空心方块 | `render()` 按图层排序遍历实体，破坏了绘制层次（先画格构后画底色，底色盖住了格构） | 严格按**编写顺序**遍历，不排序 | 以后加新图层仍须保证顺序 |
| G2 | 管线里有多余内线 | 空心矩形当成两个矩形画 | 画成一个闭合矩形，内部不画 | — |
| G3 | 楼梯像一排座位 | 画了外框 + 平行线 | 只画两条侧边 + 踏步 + UP 箭头，不封口 | — |
| G4 | 尺寸标注显示 60000 | ezdxf 内置 `"EZDXF"` dimstyle 自带 `dimlfac=100` | 显式 `dimstyle.dxf.dimlfac = SCALE` | 换 dimstyle 需重查 |
| G5 | **全台灯 180° 反了（对着观众）** | GDTF 符号的**镜片在 -Y**，代码按 +Y 当前方 → `rotation = aim - 90` | `rotation = aim + 90` | 见下方 §3.2 |

#### G5 的详细过程（因为它是最难抓的一类）

实测符号多边形的两端宽度：

| 灯具 | -Y 端均宽 | +Y 端均宽 | 结论 |
|---|---|---|---|
| fresnel | 237.6 | 186.2 | 镜片在 **-Y** |
| par | 87.2 | 67.7 | 镜片在 **-Y** |
| led | 315.7 | 206.7 | 镜片在 **-Y** |

**为什么其它检查全部通过：** 灯画出来了、数量对、不重叠、墨密度正常。
「朝向」是一个**独立的语义断言**，不把它单独写出来就永远抓不到。

修完之后还踩了第二个坑：`verify.py` 原本用"沿 Y 切片比两端宽度"判断朝向，
符号轮廓做 RDP 简化后点变稀疏，切片宽度不稳定 → **误报**。
改成比"两端 `|x - insert.x|` 的均值"，与点数无关。

> **教训：** 几何断言要选**对采样密度不敏感**的特征。
> 宽度、面积、极值这类积分量稳定；切片、相邻点距这类微分量不稳定。

### 3.2 排版与文字

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| T1 | 字大 1.4 倍 | em 当 cap 用 | `EM_TO_CAP`，见 §2.1 |
| T2 | 白色遮罩"没有" | 收尾避让器把 `FIXTURE_TXT` 图层的字**挪走了**，白底留在原地 | 该图层加入 `_fixed_layers`，避让器不碰 |
| T3 | 白底框盖不住字 | 按 cap 高度估框，但字形有上伸/下伸部 | 先放字 → 量**真实 bbox** → 删字 → 按 bbox 画白底 → 放回字 |
| T4 | 图签 `DIRECTOR` 和值重叠 | 换成 Arial 后字变宽（27.0mm vs Hiragino 22.1mm），硬编码的标签列宽不够 | `LBLW` 从**实际字体**测量得出，不写死 |
| T5 | 标签压在灯具符号上 | 编号偏移 3.8mm，符号半径 5–7mm | 偏移量从符号实际 bbox 算，不从常量猜 |
| T6 | 剖面右栏溢出页面 | `W` 从 100 改 60 后，`TYPE` 字段到 x=423.6 > 420 | 栏内所有字段按 `W` 相对定位 |

#### T3 的通用模式

**任何"框住文字"的需求，都不要用字号估框。**
正确顺序永远是：

```python
t = msp.add_text(...)          # 1. 先放
t.place(...)                   # 2. 定位
bb = ezbbox.extents([t])       # 3. 量真实 bbox
t.destroy()                    # 4. 删掉
draw_mask(bb)                  # 5. 按 bbox 画遮罩
t2 = msp.add_text(...)         # 6. 放回
```

代价是每个带遮罩的文字要建两次实体，但这是**唯一**能保证遮罩覆盖的方法。

### 3.3 字体

**图上永远不写中文。** 这不是审美偏好，是三条硬约束：

1. DXF 交付物必须纯 ASCII（`dxfix` 会硬失败）。中文会触发 `\U+` 转义，
   Vectorworks 不保证支持。
2. 跨平台中文字体不存在。macOS 有 PingFang，Linux 有 Noto，Windows 有雅黑 ——
   三者的 advance width 差 1.5–2 倍，任何按宽度排的版都会崩。
3. 参考图（NIDA 的 A4/A1 图）本身就是英文。要"和我这个 PDF 完全一样"，
   只能英文。

现在 `FONT = "Arial.ttf"`，`fonts.py` 只负责**探测**字体文件路径
（`make_portable()` 把 DXF 里的字体路径削成文件名，否则别人机器上找不到）。
`fonts.mpl_setup()` 已从出图路径移除 —— PDF 走 PyMuPDF，不需要 matplotlib 的字体配置。

### 3.4 输出格式（DXF / PDF / DWG）

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| O1 | PDF 里一个字都没有 | ezdxf **所有** backend 都把文字画成路径（`pipeline.py L370` 全部调 `draw_filled_paths`） | 自写 `pdfout.py`，用 PyMuPDF 原生画字 |
| O2 | PDF 不是 1:1，内容被拉伸 | `finalize=True` 把坐标范围设成 DXF extents（821×574）而不是纸张（841×594），x 放大 1.0244、y 放大 1.0348 | `finalize=False` + 显式 `set_xlim/ylim`；`verify.py` 反解图框位置验证 |
| O3 | 细线看起来丢了 | **这个论断不成立**。参考图 0.144pt，我们的 0.1417pt，差 1.6% | 无需修（记录在此防止有人重复"修"） |
| O4 | PDF 尺寸对但内容错 | `verify.py` 只查页面尺寸 —— 那是 `figsize` 决定的，永远对 | 加 `check_scale()`：反解图框实际位置与尺寸 |

#### O1/O2 的架构意义

**PDF 不是"把 DXF 渲染一遍"，是"用同一份 DXF 数据重新画一遍"。**

`pdfout.py` 逐实体读 DXF，用 PyMuPDF 的 `Shape` 重画：

| DXF | PDF |
|---|---|
| `LINE` / `LWPOLYLINE` | `Shape.draw_polyline()` |
| `TEXT` | `page.insert_text(fontsize=cap/EM_TO_CAP*K)` |
| `INSERT` | 展开块定义，按 rotation/scale 变换多边形 |
| `SOLID` / `HATCH` 白底 | `Shape.draw_polyline(fill=0xFFFFFF)` |
| 线宽（1/100mm） | `Shape` 的 `width`，直接用图纸 mm |

好处：文字可提取、线宽是真 mm、白填充是矢量实心。
代价：`pdfout.py` 是第二套渲染实现，**任何改 DXF 绘制的地方都要同步检查 pdfout。**

> 这是这套系统最大的一处**结构性重复**。目前 504 行，还能维护。
> 如果将来 DXF 实体类型增加到需要第三种（如 SPLINE、MTEXT 复杂格式），
> 应该考虑合并，而不是两边都加 case。

### 3.5 Vectorworks（六轮，详见 `docs/10-vectorworks.md`）

这里只提炼结论，过程看那份文档。

| 轮次 | 现象 | 真根因 | 修法 |
|---|---|---|---|
| 1 | `unrecognized file` | `$EXTMIN/$EXTMAX` 是哨兵值 `1e+20` | `dxfix.py` 文本级修补（ezdxf `saveas()` 会重置） |
| 2 | 仍打不开 | ① `ezdxf.new(setup=True)` 注入 25 个系统中不存在的字体样式 ② 23 个图层引用 `'CONTINUOUS'` 但表里是 `'Continuous'` | `setup=False` + 手工建线型 + 大小写修正 |
| 3 | 双击 dxf 打不开 | **Vectorworks 根本没注册 `.dxf`**（`grep -c -i dxf` Info.plist = 0），只有 DWG | 必须 `File > Import Single DXF/DWG`，且导入**空白新文档** |
| 4 | 整张图黑乎乎 | 白底遮罩用 ACI 7 = "随背景翻转" | 真彩 `0xFFFFFF`（组码 420）—— **需要 R2004+** |
| 5 | 比例差 25 倍 | 模型空间画的是图纸 mm | `to_model_scale()` 放大到真实尺寸 |
| 6 | 图只占页面一半 | **`$PLIMMAX` 还是 A3 的 420**，内容 841 | 四处对齐：`$LIMMAX` / `$PLIMMAX` / `$EXTMAX` / layout paper |

**两个技术细节值得单独记：**

**R2000 会丢掉 true_color（实测）：**

```
R2000: 420 tag in file=False   reload true_color=None
R2004: 420 tag in file=True    reload true_color=16777215
```

所以版本只能定在 **R2004 (AC1018)**。降到 R2000 会让白遮罩退回 ACI 7 → 变黑。

**ezdxf 在 `saveas()` 时重置四个 header 变量：**

```
$EXTMIN  $EXTMAX  $LIMMIN  $LIMMAX
```

内存里设了没用，必须在**文件写完之后**做文本级修补。`dxfix.py` 的全部存在理由。

> **坑中坑：** 修补 header 不能写 `re.sub(r"\n\s*20\n", ...)` 这种正则。
> 我写过一版把换行吃掉了，DXF 结构损坏，报
> `Missing required y coordinate near line: 38`。
> 正确做法是**按 tag 对解析**（组码 + 值），`dxfix.py` 里的 `_parse_tags`。

### 3.6 自检本身的失效（最重要的一节）

**自检会给你假绿灯。** 这是这套系统里最危险的失效模式 —— 因为它让你停止怀疑。

已发现的假绿灯，以及每个的堵法：

| 假绿灯 | 现象 | 堵法 |
|---|---|---|
| **假 1** PDF 空白但全绿 | `dxf.get("family")` 抛异常被 `except` 吞掉，所有文字被跳过 | `hasattr` 守卫 + **未知实体类型要计数对账** |
| **假 2** 黄金图 SSIM = 1.0 | 裁块坐标标错，两边都裁到空白 → 两块纯白 → 完美相似 | `MIN_INK = 0.008`：任一裁块墨密度 < 0.8% 直接 FAIL，并明确报"这不是完美匹配" |
| **假 3** 页面尺寸对但内容拉伸 | `verify.py` 只查 PDF 页面尺寸 | `check_scale()` 反解图框实际位置与尺寸 |
| **假 4** 灯全反了但全绿 | 数量、位置、重叠、墨密度全过 | 独立断言 `check_fixture_aim()` |
| **假 5** 黄金图基准不存在 | `data/golden.json` 缺失时，"掉分"分支静默跳过，只剩绝对阈值 | **这次补上了**：`--bless` 生成基准，现在会比对"掉了多少" |

**假 5 的发现过程值得记：**
`AGENT.md` 的文件地图里写着 `data/golden.json 黄金图基准`，
但文件根本不存在。代码里 `if os.path.exists(BASE)` 静默跳过。
**文档描述了一个不存在的保护。** 这类"文档与现实不符"比代码 bug 更难发现，
因为读文档的人会以为有保护。

> **给下一个 agent 的动作：** 每次改完，随机挑一条 `docs/` 里的断言去实测一次。
> 文档会漂移，代码不会说谎。

## 4. 三道门的原理与盲区

### 门 1 `src/verify.py` — 几何与像素

**原则：重新打开产出的文件验，不信内存里的对象。**

53 个断言调用点（本次运行实际输出 43 条，其余按场景/文件条件跳过），分四层：

| 层 | 查什么 | 手段 |
|---|---|---|
| DXF 结构 | 实体数、文字数、块引用数 | `ezdxf.readfile()` |
| DXF 几何 | 零重叠、全在图框内、灯具数量、剖切标注、比例尺 | 真实 bbox 两两求交 |
| DXF 语义 | **灯具朝向**、桁架腹杆数、管线空心 | 变换到图纸坐标后测量 |
| PDF | 页面尺寸、内容 1:1、墨密度、局部最密 | `pymupdf` 反解 + 600dpi 裁块 |

**盲区：**
- 不知道"设计对不对"（灯选对了吗？光打对地方了吗？）—— 只验形式
- 不知道"好不好看" —— 墨密度只能抓"糊成一片"和"几乎空白"
- 颜色只验存在性，不验色相是否符合设计意图

### 门 2 `tools/golden.py` — 黄金图回归

**原理：** 从参考 PDF 和当前出图各裁同一构件，算 SSIM。

三个构件，阈值 0.60：

| 构件 | 参考坐标（mm，原点左上） | 当前坐标（mm，原点左下） | 分数 |
|---|---|---|---|
| `truss_cell` | (54.19, 58.3)–(66.5, 71.5) | (120.0, 421.5)–(133.0, 435.5) | 0.680 |
| `truss_run` | (150.0, 58.0)–(174.0, 72.0) | (300.0, 421.5)–(324.0, 435.5) | 0.632 |
| `fixture_block` | (700.6, 515.0)–(745.0, 545.0) | (205.0, 172.0)–(249.0, 202.0) | 0.781 |

注意两边的**原点不同**：参考图是 PDF 坐标（原点左上），
当前出图是 DXF 坐标（原点左下），`_crop_gray(flip_y=...)` 处理这个差别。

**坐标是实测的，不是猜的。** 探针脚本见 `docs/09-selfcheck.md`。

**盲区（必须知道）：**
- 只比三个小构件，**不是整图比对**。整图 SSIM 会被版式差异淹没，没有信号。
- 阈值 0.6 很低 —— 因为参考图是**别的场地、别的灯具**，形状对但内容不同。
  0.6 抓的是"桁架节距和画法像不像"，不是"图一样不一样"。
- 换项目/换参考图必须重跑 `--bless`。

### 门 3 `src/hsc.py` — NESA 合规

按 NESA Drama Stage 6 Syllabus (2009) Design 选项逐条查。
实跑输出 10 行 = **8 项可机检 + 2 项人工确认**：

1. rationale ≤ 300 词，且符合 4 段式 DoE 结构
2. 平面图 ≥ 3 张（主图 + 2 场景）
3. 比例 1:25（硬性）
4. 两个场景必须**形成对比**（色片差 ≥1 项或强度差 ≥2 项）
5. Cue sheet 存在且非空
6. Running script 的 beat 与 cue **一一对应**
7. 有 acting zones 标注
8. 每台灯有 `purpose`（照哪里）
9. 装裱无玻璃（**不可机检，只能提醒**）
10. 原创声明已签（**不可机检，只能提醒**）

**盲区：** 只验"材料齐不齐"，不验"设计好不好"。NESA 评分的主体是后者。

## 6. 已知死路：**不要重做这些**

这一节比任何"最佳实践"都值钱。

| 死路 | 为什么是死路 | 证据 |
|---|---|---|
| 换 ezdxf 的 PDF backend | ezdxf **所有** backend 都把文字画成路径（`pipeline.py L370`） | `mutool draw -F txt` 返回空 |
| 用 matplotlib 出 PDF | 线宽按 pt 走不按图纸 mm；白填充是 hatch 图案不是 SOLID；`finalize=True` 会破坏 1:1 | 见 `export.py` 顶部注释与 §3.4 O2 |
| 降到 DXF R2000 求兼容 | true_color（组码 420）在 R2000 不存在，白遮罩会退回 ACI 7 → 整图变黑 | 实测 `420 tag in file=False` |
| 用 Vectorworks MCP / GUI 脚本自动导入 | AppleScript `run Python script` 只在部分情况可用（`-609 connection invalid`）；`ImportSingleDXFDWG` 会阻塞在模态对话框上 | 实测多次 |
| 用 `libredwg` 的 `Duplicate handle 1F` 报错判断文件是否有效 | **ezdxf 的所有输出都有这个**，一行最小文件也能复现 | 最小复现文件 |
| 在 DXF 里保留中文/`±`/`©` | `dxfix` 硬失败是**故意的**。`\U+` 转义 Vectorworks 不保证支持 | 用 `+/-0`、`(C)` |
| 靠"看起来不错"验收 | 假绿灯已经出现过 5 次（§3.6） | — |
| 让模型直接生成绘图代码 | 打地鼠，见 §1.2 | — |

## 8. 如果你要修剪这套东西：安全边界

### 8.1 可以放心动的

- **`data/*.yaml` 的内容** —— 这是设计域，改动不影响代码
- **`paper.py` 的数值** —— 但改完必须重跑 `golden.py` 并重新 `--bless`
  （视觉语法变了，旧基准没意义）
- **`docs/` 的自由度** —— 文档不参与构建
- **删死代码** —— 但要先跑一遍 `./run.sh` 存基线，删完对比输出是否字节级相同

### 8.2 动之前必须想清楚的

| 你要改 | 会连带破坏 |
|---|---|
| `paper.FS` 字号 | `metrics.width_mm()` 的输入变了 → 所有按字宽算的版式（图签列宽、表格列宽、标签避让）全部要重算 |
| `render.py` 的绘制顺序 | 桁架/管线/遮罩的层次（G1）。**不要按图层排序** |
| `PDF 后端`（`pdfout.py`） | 它是第二套渲染实现，改 DXF 绘制必须同步改它，否则 PDF 和 DXF 不一致 |
| `dxfix.fix_dxf()` | Vectorworks 能不能打开全靠它。改完必须实测导入 |
| `qc.check_rig()` 的规则 | `run.sh` 第 1 步是硬门禁，加规则会让现有数据可能跑不过 |
| `verify.py` 的断言 | 松一点会放行错图，紧一点会误报正确图。**误报比漏报更快摧毁信任** |
| `data/golden.json` | 它是回归基准。手改它等于取消回归 |

### 8.3 改动后的验收顺序（固定）

```bash
./run.sh --check          # 1. 数据层：不通过就停，别浪费时间
./run.sh                  # 2. 全套：看"复核通过 / 黄金图比对通过 / 全部可机检项通过"
.venv/bin/python tools/golden.py   # 3. 确认分数没掉（掉 >0.06 会 FAIL）
```

三条都绿才算改完。**只看"跑通了没报错"是不够的** —— §3.6 说过，
这套系统历史上出现过 5 次"全绿但是错的"。

### 8.4 加新功能的正确姿势

1. **先问：这是数据问题还是几何问题？**
   数据 → 加 YAML 字段 + `qc` 规则。几何 → 加绘制函数。
2. **几何新功能必须同时加一条断言。**
   没有断言的几何 = 下次重构时会静默坏掉的东西。
3. **断言要选积分量**（宽度、面积、极值），不要选微分量（切片、相邻点距）。
   见 §3.1 G5 的教训。
4. **加完跑三次**：`./run.sh` 两次（确认确定性）、`--check` 一次。

## 9. 一句话总结

> 这套系统真正的产出不是那 8 个 PDF，
> 是**"当没人看图的时候，图仍然是对的"**这个性质。
>
> 所有看起来绕的设计 —— AI 只填 YAML、三道门禁、`dxfix` 文本级补丁、
> `pdfout` 重新实现一遍渲染 —— 都是在为这个性质付代价。
>
> 修剪的时候，先问"删掉这个，那个性质还在吗"。
> 在，就删。不在，就别动。
