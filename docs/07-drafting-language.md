# 07 — 图纸视觉语法（从 NIDA 参考图实测反推）

> 这一页记录的是**怎么让图看起来像专业图纸**，不是"怎么画得更花"。
> 所有数字都是从 `brief/reference/XMACH_LXGRID_JC_v5.pdf`（A1 594×841mm）
> 用 pymupdf 提取矢量路径后实测得到的。

---

## 0. 一句话总结

参考图的"专业感"来自三件事，跟颜色、渐变、阴影毫无关系：

1. **线宽动态范围 28:1**（0.025mm 到 0.713mm），不是统一 0.15mm
2. **白底遮罩做"断裂"**（1492 处白色填充），让符号和文字永远压不断
3. **字号分层错落**（14mm 标题 → 3mm 色片号），不是全图一个字号

## 1. 线宽：10 级，28:1

实测参考图 2735 条路径的线宽分布：

| pt | mm | 数量 | 用途 |
|---|---|---|---|
| 0.07 | 0.025 | 108 | 尺寸线、极细辅助 |
| **0.14** | **0.049** | **842** | **桁架、座位、光区框** |
| 0.24 | 0.085 | 8 | 符号内部细节 |
| 0.29 | 0.102 | 22 | — |
| 0.36 | 0.127 | 28 | 布景细节、引线 |
| 0.43 | 0.152 | 476 | 主体线 |
| 0.50 | 0.176 | 119 | 设备轮廓 |
| 0.58 | 0.205 | 13 | — |
| **0.72** | **0.254** | **281** | **灯具符号轮廓** |
| 2.02 | 0.713 | 45 | 图框 |

**关键洞察**：桁架用的是**最细的 0.049mm**。桁架很长，用粗线会压住整张图。
灯具符号用 0.254mm（粗），因为它是视觉主体。

代码：`src/paper.py` 的 `LW` 字典。注意 DXF 只接受固定线宽枚举值，
`paper.lw()` 会把设计意图吸附到最近合法值。

## 2. 颜色：只有黑色

实测：黑色 1934 条、深灰 8 条、**彩色 0 条**。

我早期版本用红色画剖切线、蓝色画光区、红色画 DIM 层 —— 全错。
参考图的层级完全靠**线宽 + 字号**表达，不靠颜色。

现在：`paper.py` 里 `BLACK = 250`（ezdxf 7 号色），只有 DIM/ZONE 用 `GREY = 8`。

## 3. 白底遮罩 = "断裂"的实现方式

参考图 2735 条路径里，**1492 条带白色填充**。它们不是装饰，是遮罩：

```
桁架线 ──────────┬──────────┬──────────
                 │ SPEAKER  │          ← 白底方块盖住线
                 └──────────┘
```

看起来像"线在方块边界处精确断开、另一侧继续"，实际是白色填充在遮挡。
这比真的把线裁断简单得多，而且缩放/编辑时不会露馅。

实测证据：`SPEAKER` 方块尺寸 46.8 × 9.7mm（80 个），下面有一条 0.5pt 的点线。

**代码**：`src/draw.py` 的 `Pen.mask()` / `mask_rect()` / `mask_circle()`。

**顺序铁律**：白底必须先画。`paper.DRAW_ORDER` 定义了顺序。

## 5. 灯具标注的三层语法

实测参考图（R119 / L603 那一组）的排法：

```
      ╭───╮              ← 灯具符号（双线轮廓 + 白底）
      │   │
      ╰───╯
        │   ← 引线
       ⓞ    R119        ← 圆圈=通道号（USITT §6.14.1）
            L603        ← 色片号，正下方成两行块
```

三个要点：

1. **通道号在圆圈里**。USITT RP-2 §6.14.1 规定圆形 = Channel。
   裸数字不符合规范，也读不清。
2. **编号 + 色片号成两行块**，放在圆圈右侧。行距按字高 × 1.28（实测系数）。
3. **三者不在同一条竖线上**，所以不挤。

### 为什么必须做成 BLOCK

早期版本把圆圈、编号、色片号画成三个独立 TEXT，然后让排版器逐个避让。
结果排版器为了消除重叠，把编号和色片号拉到了不同高度，**拆散了成组关系**。

现在每台灯的标注是**一个匿名 BLOCK**（`LBL_<unit>`），整组插入。
排版器要么整组移动，要么不动。

## 6. 排版避让：两级约束 + 真实包围盒收尾

`src/layout.py` 分三层：

**第一层：估算避让**（`Layout.resolve`）
- 硬约束：文字压文字、文字出图框 → 失败则 raise
- 软约束：文字压布景/桁架 → 尽量避让，避不开就接受

**第二层：真实包围盒收尾**（`Layout.resolve_real`）
- 用 `ezdxf.bbox` 实测每个 TEXT 的真实包围盒
- 发现重叠就把低优先级的下移一个字高，迭代到干净

**为什么需要第二层**：字体真实度量比估算宽 **1.57 倍**（中位）、高 **1.28 倍**。
实测 287 个文字实体校准出来的：

```
宽度比 实际/估算：中位 1.572，90 分位 1.675，最大 2.227
高度比 实际/字高：恒为 1.276
```

只靠估算永远会残留少量压字。必须实测收尾。

**踩过的坑**：ezdxf 里非左对齐的文字，位置存在 `align_point` 而不是 `insert`，
直接改 `dxf.insert` 不生效。必须用 `get_placement()` / `set_placement()`，
而且 `get_placement()` 返回的是 `(align, p1, p2)` 三元组。

## 7. 桁架：双线 + 端头三角格构

参考图的桁架不是实心斜线填充，是：

- **两条平行的细线**（0.049mm）
- 中间**白色填充**（遮住下面的东西）
- **端头一小段三角格构**（表示"这是桁架不是圆管"）
- 长桁架每隔一段画一个之字斜撑

实测尺寸：桁架条 11.3pt ≈ 4mm 宽。

**不要**整条铺满连续 Z 字斜撑 —— 那样会变成一团乱线（我早期版本就是这个毛病）。

代码：`draw.truss_bar()` / `draw.truss_end_cap()` / `draw.truss_mid_pattern()`。

## 10. 桁架的真实构造（实测 Prolyte / NIDA）

### 10.1 参考图实测

从 `XMACH_LXTrussPlan` 的矢量路径直接量出来：

```
单元 = 34.08 × 34.08 pt（1:1 正方形）
弦杆高 = 5.76 pt  = 0.169 × 单元
竖杆宽 = 2.88 pt  = 0.085 × 单元
斜撑厚 = 2.64 pt  = 0.078 × 单元
线宽   = 0.144 pt = 0.0508 mm
```

**斜撑是平行四边形，不是线**。四个顶点（归一化，y 从顶算）：

```
左斜撑: (0.479,0.063) (0.085,0.901) (0.162,0.937) (0.556,0.106)
右斜撑: (0.535,0.063) (0.930,0.901) (0.852,0.937) (0.458,0.106)
```

斜撑两端**伸进弦杆内部**（y=0.063 / 0.937），但弦杆最后画
（白底 + 描边），把斜撑端头盖住 → 视觉上 Λ 顶点正好贴住上弦下边缘。

**绘制顺序铁律**：斜撑 → 竖杆 → 上下弦。顺序错了会露出斜撑端头。

### 10.2 与真实厂商 CAD 的对照

下载并检查了两个真实厂商的桁架 CAD：

| 来源 | 格式 | 内容 | 结论 |
|---|---|---|---|
| Prolyte H30V/H40V | DWG (AC1027) | 11 个拐角段，**纯 3DSOLID** | 无法直接取 2D |
| Global Truss F34 | DWG | 38 个直线段，**32 条 LINE 中心线** | 可读，但只有中心线 |

Global Truss F34 的真实几何（从 SQ-4111.dwg 提取）：

```
长度 1400mm，截面 240 × 240mm，节距 250mm
弦杆 4 条（Y=0/240, Z=0/240）
斜撑 X 形交叉
```

**注意**：F34 是 **X 形斜撑**，不是参考图的 **M 形（Λ）**。
两种都是真实桁架类型：
- M 形（Λ）= 单斜撑，Prolyte S36V / NIDA 用的那款
- X 形 = 交叉斜撑，Global Truss F34

本工具链按**参考图的 M 形**实现，因为那才是标杆。

### 10.3 关键教训：线宽单位

ezdxf 的 matplotlib 后端把 DXF 线宽（1/100mm）换算后**直接当 pt 写出**，
没有做 mm → pt 转换。结果是整张图细 2.83 倍。

```python
# 错：整体细 2.83 倍
Configuration(lineweight_policy=LineweightPolicy.ABSOLUTE, lineweight_scaling=1.0)

# 对
Configuration(lineweight_policy=LineweightPolicy.ABSOLUTE,
              lineweight_scaling=72.0/25.4, min_lineweight=0.02)
```

修正前后 PDF 线宽实测：

| 用途 | 修正前 | 修正后 | 参考图 |
|---|---|---|---|
| 图框 | 0.700pt | 1.984pt | 2.016pt ✓ |
| 灯具符号 | 0.250pt | 0.709pt | 0.720pt ✓ |
| 桁架 | 0.050pt | 0.142pt | 0.144pt ✓ |

### 10.4 灯具符号与标注布局

参考图的排法（实测文字坐标）：

```
        ╭─────╮          ← 灯具符号（GDTF 提取，含吊架）
        │     │
        ╰──┬──╯
           │             ← 引线
          ⓞ              ← 通道号圆圈（USITT §6.14.1）
         204             ← 灯具编号
        L132             ← 色片号
```

三个要点：
1. 圆圈在符号**正下方**（沿 -出光方向），距符号半长 + 圆圈半径
2. 编号与色片号在圆圈下方，**同 x 居中**，行距 = 字高 × 1.30
3. 全部文字**水平**，不随灯具旋转（旋转后倒读是错的）

符号挂载：灯具从桁架**下沿**挂下，插入点沿出光方向偏移
`桁架高/2 + 符号半长`。

## 11. 两个假绿灯的教训

这一轮返工暴露了两个「检查器说有、实际没有」的假绿灯。都记下来。

### 11.1 检查器看不见 BLOCK 里的文字

第一版 `verify.py` 只查 `msp.query("TEXT")`。但灯具标注被做成了
`LBL_<unit>` block（为了成组移动），里面的圆圈、编号、色片号都在
**block 定义**里。modelspace 层根本查不到。

结果：检查器报「零压字」，图上却是一片重叠。

**修法**：`entity_bboxes()` 必须展开 INSERT，把每个 block 引用当成
一个整体包围盒参与碰撞检测，同时块内文字要单独检查。

```python
# 错：只看 modelspace 的 TEXT
for e in msp.query("TEXT"): ...

# 对：TEXT + MTEXT + INSERT 全都收进来
for e in msp:
    if e.dxftype() in ("TEXT", "MTEXT"): add(e, "TEXT")
    elif e.dxftype() == "INSERT":        add(e, "INSERT")
```

### 11.2 线宽单位换算错了 2.83 倍

ezdxf 的 matplotlib 后端把 DXF 线宽（1/100 mm）换算后**直接当 pt 写出**，
没有做 mm → pt。整张图细 2.83 倍，看起来像草稿。

```python
lineweight_scaling = 72.0 / 25.4     # 必须乘这个
```

验证方法：量产出 PDF 的线宽，和参考图对比。修正后完全对上：

| 用途 | 修正前 | 修正后 | 参考图 |
|---|---|---|---|
| 图框 | 0.700pt | 1.984pt | 2.016pt |
| 灯具符号 | 0.250pt | 0.709pt | 0.720pt |
| 桁架 | 0.050pt | 0.142pt | 0.144pt |

## 12. 右栏排版密度

参考图实测：

- 图例文字 12pt（4.2mm），**行距 21pt（7.4mm）** → 行距 = 1.76 × 字高
- 面板按内容自适应高度，**不留大片空白**

早期版本行距 12.6mm（松了 70%），且面板固定高度 → 表格里空得能跑马，
或者文字挤成一团。现在按 `panel_height(nrows)` 算：

```python
def panel_height(nrows):
    return 8.0 + HDR_H + nrows * ROW_H + PANEL_PAD
```

图签同理：不再固定 163mm 高，而是从灯具表底边一直延伸到纸边，
剩余空间填「备注区」，不留空白。

## 13. 墨密度作为客观指标

用像素统计代替「看起来对不对」：

```python
pix = page.get_pixmap(dpi=300)
dark = (np.array(img) < 128)
overall = dark.mean()
# 分 8×12 块，找局部最密
```

实测对照：

| 图 | 墨密度 | 局部最密 |
|---|---|---|
| 参考 LX Grid | 0.0261 | 0.0770 |
| 参考 Truss Plan | 0.0118 | 0.0881 |
| 本工具链平面图 | 0.0243 | 0.0706 |
| 本工具链剖面图 | 0.0218 | 0.0757 |

阈值：整体 > 0.12 判「太黑」，局部 > 0.30 判「视觉拥挤」。

这个指标能抓住几何检查漏掉的问题——比如文字虽然没互相压，
但压在细线上导致读不清。
