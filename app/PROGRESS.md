## 2. 关键决策（以及为什么）

### 2.1 几何只生成一次，多个后端只负责"画"

旧管线有 DXF（ezdxf）和 PDF（手写 pdfout.py）两套独立渲染实现，
技术报告称其为"最大的一处结构性重复"。

现在：`PlanBuilder` 生成 `[DrawOp]` 指令列表 → `SheetPDF`（CoreGraphics）、
将来的 `CanvasView`（SwiftUI）、`SheetDXF` 各自只需实现"把指令画出来"。

**副作用是巨大的好处**：指令列表本身可断言 —— 灯数、多边形数、文字数、
包围盒、朝向，全部能在测试里数出来。GUI 因此变得可精确测试。

### 2.2 文档格式宽松解码、严格校验

旧 `qc.py` 是"数据不全就 raise"，批处理里对，编辑器里是灾难
（拖了一半的文档打不开就没法继续改）。

现在所有字段 optional，永远能加载；`Lint` 用**稳定错误码**报告缺什么。
严格程度没降，只是从"拒绝加载"变成"标红提示"。

### 2.3 灯具坐标是"沿杆绝对轴值"，不是"距杆端偏移"

`x` 是绝对世界坐标，`y` 由构件给。所以解析时**不能夹紧**：
灯挂在杆外就按实际坐标画出来，由 `Lint` 报 `fixture.offPosition`。
悄悄夹紧会让图与数据不一致，比报错更危险。

歧义状态（两个坐标都给）按轴线解，同时报 `fixture.ambiguousMount`。

### 2.4 比例锁死 1:25，只移动图框原点

`SheetLayout.fitted()` 只居中，不缩放。放不下时 `contentFitsSheet == false`，
`lpx render` 打印警告 —— 溢出必须可见，不能悄悄裁掉。

### 2.5 字体度量必须归一化成 em

`CTLineGetTypographicBounds` 返回**点**，必须除以参考字号才是 em。
漏掉这一步，所有按字宽排的逻辑会放大 1000 倍，而画面上的字看起来正常。
这个 bug 被 `Title block carries every metadata field` 测试抓到过。

## 4. 灯具朝向：推翻了旧项目的结论

旧项目注释说"所有类型镜片都在 -Y"，并在代码里用 `rotation = aim + 90`。
**这不成立。** 用剖面法（沿长轴 20 段，量每段横截面最大宽度）实测：

| 类型 | 长轴 | head(4段) | tail(4段) | 判断 |
|---|---|---|---|---|
| par | Y | 5.3 | 62.4 | 细臂(yoke)在 head ⇒ 后方 -Y ⇒ **前方 +Y** |
| fresnel | Y | 22.6 | 185.5 | 同上 ⇒ **前方 +Y** |
| follow | Y | 188.0 | 155.9 | 宽镜面在 head ⇒ **前方 -Y** |
| profile | Y | 182.9 | 184.6 | 两端近似对称，**几何无法判定** |
| led / mover | X | 165.6 | 165.6 | 左右镜像对称，**几何无法判定** |

**统一规则**：U 型托架（细臂）在灯具**后方**。

因此朝向不能靠自动测量（profile 会给随机答案、led 会拿短轴当长轴），
必须**按类型声明**（`FixtureOrientation.forward`）。

结果：profile / led / mover / follow 与旧管线一致；
**fresnel 与 par 各 6 台被纠正**（旧管线把它们装反了，出光朝观众方向）。

## 4.6 剖面图（已完成，比平面图复杂）

`Sources/LightPlotCore/Section/`：
- `SectionLayout` —— 剖面坐标系。**横轴 = 纵深，纵轴 = 高度**，
  与平面图相反，换向只在这一处做。
- `SectionGeometry` —— 光束包络、遮挡判定、视线计算。
- `SectionBuilder` —— 场地 / 观众席 / 布景 / 位置 / 人形 / 右栏 / 图签。

### 比旧管线多出来的三件实质内容

**1. 真实光束包络 + 焦点光斑宽度。**
旧管线画两条到"舞台中区"的斜线。现在光轴由**几何**决定（灯口 → 焦点），
宽度 = 2·tan(半角)·沿轴距离，并在焦点处标出光斑实际宽度（mm）。
沿轴宽度是物理量；"同一纵深处两条边界的高度差"不是 —— 后者在光轴倾斜时
会给出"越远越窄"的假象（这个 bug 被测试抓到并修正）。

**2. 遮挡判定。**
`SectionGeometry.blockage` 沿光轴采样，只有当光束的**完整竖向跨度**
落入某个布景矩形内才算遮挡，并在图上标 `BLOCKED <纵深>`。
剖面图是唯一能看出"光有没有被挡"的那张图，这条不能省。

**3. 视线检查（最有价值的一项）。**
每排观众的眼睛要越过前一排头顶看到台面。公式用眼高 1150 / 头顶 1250、
逐排递推。结果直接印在右栏的 `SIGHTLINES` 面板里。

> 现有数据跑出来：**7 排里 6 排被挡，最差一排差 111mm**。
> 这不是 bug —— 是 data 里 `audience_rake: 160` 确实不够
> （实测需要约 400mm/排）。测试 `realDocumentReportsBlockedRows`
> 把这个已知缺陷钉住：数据改好后它会失败并提醒更新。

### 其他细节

- 光束与视线都做 **Liang–Barsky 裁剪**，不会画到纸外
- 灯具在剖面上画成**一台代表性轮廓 + `xN` 数量**，
  而不是每台一个 1mm 小方块（1:50 下那是 0.02mm，渲染成一串点）
- BOOM 在中心线剖面上切不到，画虚线并标 `(BEYOND CUT)`
- 布景只有**被切线剖到**才画成实线剖面，否则只画一小段虚线提示

### UI

工具栏有 `Plan / Section` 分段控件，两页共用同一份文档与撤销栈。
导出按当前页决定图幅（平面 A1 @1:25，剖面 A3 @1:50）。

## 4.7 文档与场地编辑（已完成）

审计发现的真实缺口：**能打开但不能改**。
一个不能输入真实场地尺寸的绘图工具，解决不了它的核心问题 ——
所有几何都由那些数字算出来。

已补齐（`DocumentEditingTests`，15 条）：

| 类别 | 可编辑 |
|---|---|
| 演出信息 | 剧名 / 编剧 / 场地 / 导演 / 设计师 / 图名 / 日期 / 版本 |
| 场地 | 宽 / 深 / 栅顶高 / 台口高 / 台口位置 / 观众排数 / 排距 / 起坡 |
| 构件 | 名字（灯跟着改）/ 类型（truss/pipe/line）/ trim 高度 |
| 布景 | 添加平面/楼梯/墙、改高度、删除 |
| 光区 | 添加（同 id 覆盖）、删除 |
| 纸幅 | A0 / A1 / A2 / A3 |

**四条设计纪律**

1. **改场地就重算图框**（`relayoutIfNeeded`）。否则场地从 15m 改到 9m 后
   图纸会偏到一边甚至出框。
2. **非 ASCII 在编辑入口就被替换**（`EventSanitizer`）。
   常见标点做有意义的替换（`±` → `+/-`，`©` → `(C)`），
   其余变问号 —— 不静默删除，因为"少几个字"比"看到问号"更难排查。
3. **改构件名要带着灯一起改**。否则挂在上面的灯立刻变成"未知位置"。
4. **纸幅切换不改比例**，只重算原点。装不下时给出可执行建议
   （`Fits 16.6 x 13.7 m at 1:25`），而不是静默缩放。

### 这一轮抓到的真实 bug

`SheetLayout.infoColumnX` 曾是写死的绝对坐标 `700`（为 A1 定的）。
换成 A0 后平面可用宽度仍是 660mm —— **纸变大了却一点没多出来**，
用户会以为"换纸没用"。改成"从右边缘往内数 130mm"后，
A0/A1/A2/A3 的容量分别是 25.3 / 16.6 / 10.4 / 6.0 米。
`PaperCapacityTests` 把这条钉住了。

## 6. UI 布局：踩过的四个坑（写给下一个改布局的人）

iPad 上"图纸只占屏幕顶部一条 / 右边被裁一半"花了六轮才定位。
四个坑层层相扣，任何一个都会让你看不到全图：

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | 编辑器只占屏幕顶部一条 | `HStack` 里 `Canvas` 没有固有尺寸，被压到最小高度（实测 161pt） | 显式 `.frame(width:height:)` |
| 2 | 画布尺寸永远停在第一次的中间值 | 在 `Canvas` 的 **draw 闭包**里改 `@Published` —— 破坏 SwiftUI 更新周期 | 尺寸只在绘制时读，状态由 `onAppear`/`onChange` 更新 |
| 3 | 图纸右半边被检查器盖住 | 检查器用 `overlay`（不参与布局），画布仍是整宽 834pt，右 286pt 落在检查器底下 | 宽屏用 `HStack` 真正分走宽度；窄屏检查器默认**收起** |
| 4 | 图例文字糊成色块 | 缩放 0.94 时 `capMM 2.24 × 0.94 = 2.1pt`，低于可读下限 | 屏幕字号 < 3pt 不画（PDF 不受影响，它是 1:1） |

**调这类问题的正确姿势**：先在画布左上角用 `context.draw` 打印
`size / zoom / pan / 纸张映射后的矩形`，再对比截图上纸的实际位置。
不要靠"改动 → 截图 → 猜" —— 那六轮里有四轮是白猜的。

## 7.5 保存（后期补上，曾是致命缺口）

第一版只有"导出 PDF"，**没有保存**。这意味着关掉窗口就丢光工作 ——
一个不能存的编辑器不成立。现已补上：

- `EditorModel.save(to:)` / `saveInPlace()` / `open(url:)`
- `.lpx` = 稳定 JSON（键有序），适合进版本管理
- **从 `rig.yaml` 打开后 `documentURL` 保持 nil** —— 一次 Cmd-S 不会覆盖旧文件的注释与排版
- `isDirty` 由 `reduce` 的文档差异驱动，标题栏显示 "— Edited"
- 打开失败**不替换当前文档**（静默替换会让人以为文件丢了）

测试见 `PersistenceTests`（6 条）：dirty 跟踪、往返一致、旧文件不被接管、
补色不覆盖、未存过时 `saveInPlace` 失败、坏文件不崩且不改文档。

## 7.6 字体锁定（已完成，闭合了 iPad 与 Mac 的差异）

内置 **Liberation Sans**（SIL OFL）。三个实测结论：

| 项 | Arial | Liberation Sans |
|---|---|---|
| 能否随应用分发 | ❌ Monotype 商用 | ✅ SIL OFL |
| iPad 上有 | ❌ | ✅ 随包 |
| advance width（73 个字符） | — | **完全相同，MAXDIFF = 0.000** |
| cap/em | 0.7163 | 0.6880 |

cap/em 不同但**不影响字高**：`capToEm` 是从字体文件读的，
"3.04mm cap 的字"在任何字体下都是 3.04mm，只是需要的 em 尺寸不同。

### 这一轮抓到的三个真实 bug

1. **`LiberationSans-Regular` 解析失败并静默退回 Arial。**
   Liberation 的常规体 PostScript 名就是 `LiberationSans`，不带 `-Regular`。
   `CTFontCreateWithName` 找不到名字时**不报错**，直接返回系统默认字体 ——
   所以必须比对解析结果。
2. **SPM 的 `.process` 把资源打平到 bundle 根目录**，`Fonts/` 子目录是空的。
   两处路径都要找。
3. **缓存与字体注册的顺序错了。** 早先"先查缓存、后注册"，
   并发首次调用会把 Arial 写进缓存且永不更新。
   现在「注册 → 解析 → 写缓存」在同一把锁内完成，兜底结果不入缓存。
   测试连跑 5 次全绿验证。

`FontLockTests`（6 条）守着：字体文件在包里、真的用上了、
cap/em 来自文件而非硬编码、advance width 未变、摘要记录了实际字体。

## 7.7 选中 / 拖动 / 删除闭环（已完成）

审计发现的第二个真实缺口：**能添加却选不中、删不掉**。
布景与光区原本只有 `add` 事件，没有命中测试、没有选择集、没有删除入口 ——
用户加了就再也去不掉。

已补齐（`SelectionTests`，14 条）：

- `Selection.setPieces` + `Hit.setPiece`
- 命中优先级：**灯具 > 构件 > 布景 > 光区**。
  光区框最大，放最后才不会把它里面的一切都盖住。
- 布景可拖动（`moveSetPiece`），且因为 `SetPiece.id` 由坐标派生，
  移动后**选择集必须跟着更新** —— 否则用户拖一次就失去选中。
- 楼梯拖动只推下沿，保持踏步进深。
- 工具栏「删除」按钮，多选一次删除只压一个撤销点。

### 走查测试挖到的两个真实 bug

`UIActionWalkthroughTests` 把界面上每个按钮背后的动作在无头环境跑一遍，
每次都断言"文档无错误"。它抓到：

1. **`addFixture` 会产出孤儿灯。**
   放到远离任何构件的位置时，代码写了 `pos = "LOOSE"` ——
   而文档里根本没有这个构件，于是立刻 `fixtureUnknownPosition`。
   更糟的是它没改 `type`，而 `isFreeMounted` 判据是 `type == "practical"`，
   所以灯既不在杆上、也不算自由摆放，成了悬空实体。
   修法：退化为实物时同时把 `type` 改成 `practical`、
   清掉指向不存在构件的 `pos`、并把原类型记进 purpose 以免丢失意图。

2. **Lint 把自由摆放的灯误报为"缺 pos"。**
   台灯放在台上，不属于任何吊挂构件 —— 它本来就不该有 `pos`。
   假错误比漏报更危险：它训练人忽略所有错误。

## 7.8 文字重叠检查（审计才发现的方法论漏洞）

前七轮我一直在用"看起来对"验收版面。补上真正的检查后发现：

**平面图与剖面图都有真实碰撞，此前从无断言。**

平面图一直有"零重叠"的说法，但那是从旧管线 `verify.py` 继承的口头结论，
LightPlot 里**从来没有实现过**。补上之后抓到 2 处：

| 碰撞 | 原因 |
|---|---|
| 图例的灯具数量 "2" ✕ 图框分区号 "2" | 信息栏右边界等于 `innerFrame.x1`，压在分区带上 |
| 竖直 BOOM 的名字 "BOOM SL" ✕ 分区字母 "I" | 构件名按法向偏移后落入分区带 |

剖面图更严重，抓到 5 处：剖切标记 "A" 压在观众席图形上、
四个位置的光斑宽度标签在地板上叠成一团、
同一位置左右两台边界灯的光斑标签落在**完全相同的坐标**
（实测 bbox 一模一样 —— 因为焦点纵深与光束角都相同）。

### 修法

- 平面图：信息栏内缩 10mm；光区/构件名夹到安全区内
- 剖面图：剖切符号改成 USITT 惯用箭头 + 空心三角，沉到内框与绘图区之间的留白带
  （分区号在 `innerFrame+6.4`，符号压在 `innerFrame+3.2`）
- 光斑标签：**每个位置只标一次**，并按位置序号纵向错开
- 绘图区比内框再内缩 8mm（原来两者完全重合，内容顶到框线）

### 教训

> **「看起来对」不是验收标准。** 这三处碰撞都藏在小角落，
> 我自己扫图三遍没看出来，是断言替我找出来的。
>
> 断言必须是**真实 bbox 两两求交**，不是"字号乘个系数估一下"。
> 平面图与剖面图现在共用同一套检查（`Text layout` 套件，4 条）。

## 7.9 退化与溢出输入（审计发现）

上一轮修的是"正常数据下的版面"，这轮查的是**极端输入**。
新增 `Render edge cases` 套件（11 条）：空文档、无灯具、无构件、
2m 小舞台、60m 大舞台、零高栅顶、荒谬光束角、超长剧名、
零尺寸布景、四种纸幅。

### 抓到的真实缺陷：溢出时输出一张空白纸

60m 舞台塞进 A1@1:25 时，内容全部画在纸外 —— 用户得到**一张白纸**，
没有任何提示说明为什么空。这是最糟的失败方式：
看起来像程序坏了，而不是"场地太大"。

修法：`PlanSheet(fitting:)` 与 `SectionSheet(fitting:)` 在装不下时
改为输出**说明页**，而不是跑内容的空白页：

```
THE DRAWING DOES NOT FIT
ON THIS SHEET
Content is  40.0 x 34.4 m
This sheet holds  16.6 x 13.7 m  at 1:25
Use a larger sheet, or a smaller scale.
(Paper and Scale are in the inspector.)
```

**不做"自动缩小比例"** —— 比例是设计要求，不该被悄悄改掉。

### 顺带修掉的第二个 bug

说明页第一版用 22mm cap 却只隔 18mm，两行大字直接压在一起。
`Text layout` 测试现在也覆盖说明页（实测第一版就 FAIL）。

## 7.10 区域冲突（第三层检查）

前两层查「文字 vs 文字」「退化输入」。这层查**区域 vs 区域**：
平面内容有没有压进图例栏、剖面绘图区有没有压进右栏。
这类冲突比文字重叠更隐蔽 —— 「一根桁架穿过图例」看起来只是多了一条线。

新增 `Layout region collisions` 套件（4 条）。

### 抓到的真实缺陷：剖面图右栏被光束穿过

绘图区右边界写 `x1 = 332`，而右栏左边界是
`420 - 20 - 62 - 9 = 329` —— **重叠 3mm**。
结果光束直接画进 NOTES 与 TRIM SCHEDULE 面板里。

根因是同一个数字在**两处各写一遍**：

```
SectionLayout.drawingArea.x1 = 332      ← 一处
SectionBuilder.drawPanels  X = 420-20-62-9 = 329   ← 另一处
```

修法不是把 332 改成 329，而是**让两处共用一个来源**：
`SectionLayout.panelLeft(for:)` / `panelWidth` / `panelGap`，
`SectionBuilder` 直接引用。数字只写一处，就不会再漂移。

### 顺带做的一次结构调整

`titleBlockRect` / `legendRect` 原来藏在 `PlanCanvas`（内部类型）里，
测试根本够不到 —— 于是"图签有没有越框"从来没被验证过。
现在移到 `SheetLayout` 上成为公开 API，`PlanCanvas` 只做转发。
测试立刻就能检查四张纸的图签与图例是否越框。

## 7.11 屏幕可读性（第四层检查）

前三层查的是**纸**（文字重叠、区域冲突、退化输入）。这层查**屏幕**。

根本区别：PDF 是 1:1 固定尺寸，永远可读；画布要缩放。

新增 `Canvas readability` 套件（6 条）。

### 抓到的真实缺陷：适应图纸时全部灯号消失

A1 张到 iPad（可用宽 800pt）时 `zoom = 0.95`，而色片号 cap 只有 2.24mm：

```
2.24mm × 0.951 = 2.13pt   <  3.0pt 门限  →  跳过不画
```

结果：**64 个灯号 + 32 个通道号全部消失**。
这些恰恰是图纸最重要的信息。用户看到的是一张"只有桁架和格子"的空图。

### 三次尝试才找对答案

| 尝试 | 结果 | 为什么不行 |
|---|---|---|
| ① 门限 3.0pt，跳过 | 全部灯号消失 | 最重要的信息没了 |
| ② 一律放大到 3.5pt | 2.24mm 被撑到 3.68mm（1.64×） | 灯号/色片号/通道圆圈互相压成一团 |
| ③ **保持真实尺寸，只在 <1.6pt 时不画** | 密度真实、放大即清晰 | ✅ |

**根因**：标注间距是按原始字高设计的。放大字必定挤压。
所以"让所有字都够大"在屏幕上是做不到的 ——
能做的是**让密度如实反映纸上密度**，用户放大就清楚。

实测验证：放大到 3× 后，灯号 `11/201/L132`、构件名 `LX 1`、
标高 `+6500`、通道圆圈全部清晰可读。

### 顺带修掉的标注压字

自由摆放的灯具（三角符号）标注用了符号**包围盒宽度**的一半，
而三角在尖端处宽度趋近 0 —— 实测 `OPEN / 901` 的 O 压在三角尖上。
改用 `max(width, height)` 后避让正确。

## 7.12 页面设置：尺寸可切换（用户需求）

用户原话：「多做几个页面，多选，放在页面设置之类的地方里可以调整，默认 A1」。

理解成**纸张尺寸可切换**（不是多页图纸）。已实现：

### 幅面与朝向

| 项 | 支持 |
|---|---|
| 幅面 | A0 / A1 / A2 / A3 / A4 / Letter / Tabloid（7 种） |
| 朝向 | 横向 / 纵向 |
| 比例 | 1:20 / 1:25 / 1:50 / 1:100 |
| **默认** | **A1 横向 @ 1:25** |

`PaperSize` 存的是**实际宽高**，所以横向只是宽高对调 ——
渲染、比例尺、图框全都不用关心朝向，只有"选尺寸"这一层需要知道。

### 面板设计

独立的 macOS sheet（`PageSetupPanel`），⌘⇧P 打开，不是塞在侧栏里的下拉：

- 左边：幅面 / 朝向 / 比例三段选择器 + **数字结果**
  （纸多大、绘图区多大、能装多大的场地、你的内容多大）
- 右边：**纸面比例预览** —— 直接画出纸张轮廓、内框、绘图区、
  信息栏位置，用户一眼看到"图在纸上占多少"
- 底部：Cancel / Apply。**暂存后点 Apply 才写回** ——
  用户可以试几种尺寸看容量，不产生一串撤销点
- 一次 Apply 只压**一个**撤销点（改纸+改比例是一件事）

### 顺带修掉的真实缺陷

`infoColumnWidth` 原来是固定 130mm。放到 A4 上，信息栏会吃掉一半宽度，
绘图区只剩几十毫米 —— 图就废了。
现在小纸按纸宽同比收窄（下限 46mm），**大纸保持 130mm 不再放大**
（实测 A1 从 130 加到 152 反而让平面少了 22mm 容量）。

### 溢出处理

A3@1:50 或 A1 纵向装不下 16.5m 舞台时，输出**提示页**而不是空白纸：

```
THE DRAWING DOES NOT FIT ON THIS SHEET
Content is  16.5 x 13.4 m
This sheet holds  15.5 x 12.4 m at 1:50
Use a larger sheet, or a smaller scale.
```

提示里的"这张纸能装多少"是**算出来的**，用户照着改就行。

## 7.13 吸附反馈与优先级（审计发现）

### 缺陷 1：吸附完全看不见

`Snapper` 内部一直在吸附，但 UI **从不显示吸到了哪里**。
用户拖动构件端点时只能猜 —— 而吸附是这套编辑器最核心的交互，
看不见就等于没有。

已补：`EditorModel.snapPreview` + 画布绘制
（准星 + 空心圈 + 类型标签 `END` / `ON BAR` / `GRID` / `ALIGNED` / `LANTERN`
+ 到鼠标原始位置的虚线引线）。

引线是必要的：吸附点常常离鼠标有一段距离，只画准星会让人以为鼠标飘了。

### 缺陷 2：吸附优先级被距离覆盖

原实现：

```swift
if d < best.distance || (d <= radius && newRank < existingRank) { ... }
```

第一个条件让**任何更近的点**无条件胜出，于是更近的网格点
击败了稍远的构件端点。后果很实际：
**想把两根桁架接起来时，端点吸附永远抢不过网格** ——
而"接桁架"正是端点吸附存在的理由。

修法：按 `(rank, distance)` 字典序取优 —— 低 rank 永远赢，
同 rank 才比距离。`SnapPriorityTests`（8 条）钉住：

| 断言 | 内容 |
|---|---|
| 端点 > 网格 | 即使网格更近 |
| 灯具槽 > 轴线 | |
| 轴线 > 网格 | 且落在杆中心线上 |
| 同类型取最近 | |
| 对称性 | 左右等距吸附到同一点 |
| 半径以屏幕点定义 | 放大后同样的图纸偏移吸不上（hips 真实） |

### 顺带确认

应用在 macOS Release 下**能正常常驻运行**（PID 存活、无崩溃报告）。
早先我用 `open -n` + `ps grep` 判断，误判为"没启动"——
实际是 `open` 返回后进程名匹配方式不对。改为直连执行 + `pgrep -f` 确认。

## 7.14 场景系统（审计发现：整块功能缺失）

审计「旧管线产出什么 vs LightPlot 产出什么」时发现的**整块缺失**：

旧管线出 **3 张平面图**（`LX_plan` / `LX_plan_kitchen` / `LX_plan_boston`），
LightPlot 只出 1 张。而设计任务书**明确要求"两个形成对比的场景"**。

### 数据模型

`data/scenes.yaml` → `LightingStateSet`：

| 字段 | 含义 |
|---|---|
| `gel_override` | 某色片在本场景换成另一个（L132 → L202） |
| `levels` | 每个构件（FOH/LX1/LX2/LX3/BOOM/SET）的强度 0–100 |
| `default_level` | 未列出的构件用这个 |
| `concept` | 设计意图（**不印在图上**，见下） |

`SET` 是虚拟构件，代表台上实物灯（冰箱、台灯）—— 它们不属于任何吊杆，
但同样要算强度。

### 命名：`Scene` 必须改叫 `LightingState`

SwiftUI 也有 `Scene`（App 的 body 返回类型），直接撞名编译失败。
改名不是妥协 —— **LightingState 本来更准确**：
它是"某一场戏里光的组织状态"，不是舞台布景。

### 渲染

分场景平面图上，每台灯显示的是**该场景实际使用**的色片，不是基础色片。

> 这是最致命的一类错误：分场景图印错色号 —— 图看起来正常，
> 灯光师按图装片却装错。

实测：基础图 6 个 `L132`；kitchen 变 6 个 `L202`；boston 变 6 个 `L103`。

### 两个修掉的版面缺陷

1. **场景横幅压住图框分区号**（`1` `2`）—— 上一轮加的重叠检查抓到的。
   横幅下移到内框内 12mm。
2. **场景概念文字被画进图里** —— 它是中文长句，而图上必须纯 ASCII
   （`dxfix` 会硬失败）；而且一整段话盖住了光区标签 `K1`。
   概念属于 rationale 文档，不是图面标注。已移除绘制。

### 对比度检查

`LightingStateSet.contrast(a, b, doc:)` 量化两项：
- 换了几台灯的色片
- 有几个构件强度差 ≥15

`isSufficient = 色片差 ≥2 或 强度差 ≥2`。
真实数据：**色片差 16 项、强度差 3 项** → 对比充分。

### 命令行

```bash
./lpx scene data/rig.yaml data/scenes.yaml out_lpx
# 为每个场景状态出一张 A1 平面图
```

用户打不开、看不到、比不了两个场景。这是"功能存在但不可用"。

### 对比检查直接显示给用户

```
SCENE
  KITCHEN / NIGHT        ▾
```

## 7.16 表格导出（审计发现的第二处整块缺失）

审计「旧管线产出 8 个 PDF + 3 个 CSV，LightPlot 产出什么」时发现：
**LightPlot 完全没有 CSV 导出。**

而灯具表是施工必需 —— 装灯的人要的是"哪台灯挂哪根杆、装什么色片、
接哪个通道"。这些在一张 A1 上挤不下，必须另有清单。

### 现在导出 4 类表

| 表 | 列 | 用途 |
|---|---|---|
| `instrument_schedule` | POS,UNIT,TYPE,BEAM,GEL,PURPOSE,CH[,WATT] | 装灯 |
| `channel_hookup` | CH,POS,UNIT,TYPE,GEL,PURPOSE | 台面配接（**按通道排序**） |
| `gel_usage` | GEL,NAME,COUNT,UNITS,SCENE | 买料裁片（**只数点亮的灯**） |
| `scene_levels` | POSITION,<各场景> | 场景对比（一眼看出哪根杆被抽走） |

外加每个场景单独一份灯具表（色片不同，交接时不能混）。

### 三个细节

1. **UTF-8 BOM + CRLF**。不加 BOM，Excel 会把 UTF-8 当 Latin-1，
   带重音的剧名变乱码。
2. **`study` 档位不出瓦数**。学生作业里列出 750W 会让评审把注意力
   放到电学参数上，而不是光的组织。
3. **场景表按场景色片出**。基础表印 L132、kitchen 表印 L202 ——
   与图面一致，否则装片的人会按错的清单干活。

### 一个测试踩的坑

`String(contentsOf:encoding:.utf8)` **会自动剥掉 BOM**，
用它检查 BOM 永远失败。必须读原始字节比对 `EF BB BF`。

## 7.17 场景密钥错配（最危险的静默失效）

给剖面图接场景时发现：**强度数据一直没生效，整个场景是全黑的**。

### 根因

| 文件 | 键名 |
|---|---|
| `scenes.yaml` | `FOH` / `LX1` / `LX2` / `LX3` |
| `rig.yaml` | `FOH LX` / `LX 1` / `LX 2` / `LX 3` |

`levels[id]` 直接查 → **全部查不到** → 一律 `defaultLevel = 0` → 全黑。

而旧管线的 `levels` 字段**从来没人读**（只用了 `gel_override`），
所以这个错配在旧项目里也一直没暴露。

> 这类 bug 最危险：功能看起来在，数据看起来有，
> 但结果全是零，而画面依然"正常"（一张没有光的图也是一张图）。

### 修法

`level(forPosition:)` 三级匹配：
1. 精确命中
2. **归一化**（去空格/连字符/下划线、转大写）后相等
3. 前缀匹配，且**只在唯一命中时采用** —— 多个匹配说明数据有歧义，宁可退回默认

修好后 kitchen 解析正确：`FOH LX=45`、`LX 1=30`、`LX 2=0`、`BOOM SL=60`，
点亮 25/32（而不是 0/32）。

### 剖面图也吃场景

- 0% 的杆：灯具本体画**虚线**、**不画光束**
- 图名带场景：`SECTION A-A - KITCHEN / NIGHT`
- 实测 kitchen 光束从 24 条降到 18 条（LX 2 关掉）

## 7.18 检查器一致性 + 换数据测试（第七/八层）

### 检查器曾经和图面对不上

场景激活时，图上印场景色片（L202），检查器却读文档基础值（L132）。
用户会以为图错了，或者改错地方。

修法：主色块跟随 picker（基础值），下面再加**两个色块 + 箭头**
（`L132 → L202`）+ 一句 `The sheet prints the second one.`

`InspectorConsistencyTests`（4 条）同时钉住：
- 生效色片是场景的
- 未覆盖的灯保持基础值
- **退出场景回到基础值**（场景切换绝不改文档）
- 场景切换不产生撤销点（纯视图操作）

### 换数据测试揭出旧数据掩盖的缺陷

`DeliverableSetTests` 从**空白文档**造一份完整小制作
（10m 舞台 / 4 根杆 / 6 台灯 / 两个对比场景），走到六份 PDF + 六份 CSV。

它立刻抓到一个旧数据碰不到的碰撞：
`PROSCENIUM` 竖标签撞上 `LX 1` 的构件名 ——
因为那根杆的 trim 恰好等于台口高，两者落在同一高度。

修法：PROSCENIUM 标签移到台口线的**中段**（45% 高度）。
中段通常是空的，构件都在各自的 trim 上，不在半空。

> **教训：只用自己的示例数据测，会漏掉一类缺陷。**
> 尺寸、trim、台口高任意一个变化都会改变版面关系。

## 7.19 规模扫描暴露的版面缺陷（第九层）+ 一条冤枉好代码的测试

### 图例曾经列整本色库

基础图列 45 个色片，而图上只有 5 个在用。A3 的图例只有 105mm 高，
45 个色片要 280mm —— 于是图例压说明、比例尺压图例、色片行互相叠，
一个小项目一次测出 **15 处文字碰撞**。

修法：图例只列**图上真正用到**的色片。理由不是"装不下"，
而是**图例是执行依据，不是资料卡** —— 列 40 个没用的色片
只会让装灯的人以为还有别的东西要装。

### 图例框被固定成 190mm

图例里有两张表（灯具类型 + 色片），类型表 7 行就吃掉 134mm，
色片区只剩一两行，其余截成 "N more in the gel library"。
而图签上方到图框顶端之间其实还空着几百毫米。

修法：图例框用满图签上方的**全部**空间。固定高度等于把
"能装多少"硬编码进版面 —— 文档里的类型/色片一变多就必然溢出。

### 三处"想象出来的比例"

| 位置 | 写的是 | 应该是 |
|---|---|---|
| 平面图说明 | `SCALE 1:25 ON A1`（硬编码） | 实际比例 + 实际纸张 |
| 剖面图副标题 | `@ A3`（硬编码） | 实际纸张 |
| 平面图比例 | `doc.meta.scale` | `layout.scaleDenominator`（渲染时真正用的） |

打到 A3@1:50 的图上印着 "1:25 ON A1"。**一张印错比例的图比没有图更危险**
——装灯的人会照它量。修法：`PaperSize.name` 由实际宽高反推幅面名，
比例取 `layout.scaleDenominator`。

### 说明栏与图例抢同一块地方

两者都"从图签上方开始"，A3 上直接叠住（`'COLOUR' x 'SCALE 1:50'`）。
新增 `SheetLayout.notesBandHeight = 46`，图例让位。
说明栏是读图的前提，图例是可压缩的 —— 让的顺序不能反。

### 只列有灯的类型

图例早先遍历 `doc.types.keys`（整个类型表），7 个类型全画，
哪怕图上一台都没有。改成只列 `count > 0` 的类型。

### 一条冤枉好代码的测试

`OrientationTests` 里"镜片宽端朝上"那条，在我改动图例后开始失败。
数值看起来确凿（above=2.34 < below=2.57），我一度以为找到了
"全台灯反了 180°"的真回归。

**把图渲染出来看**之后发现：渲染完全正确。aim:90 光束朝后墙、镜片朝上；
aim:270 精确镜像。

错误在于那条测试的假设：它假定符号的**宽端就是镜片端**。
实际量过（并把符号单独画出来看过）才明白，
profile / fresnel / par 的**宽端是后部的喇叭形底座**，
镜片（灯罩）反而是较窄的那一端。所以"比宽度"的结论与图面相反。

改用真正的不变量：
- `drawnSymbolIsRotatedSource`（6 类型 × 8 个 aim）逐点比对
  "图上画的"是否精确等于"源符号 × 声明旋转"
- `oppositeAimsMirror` 验证 aim 与 aim+180° 精确相差 180°

> **教训：数值矛盾时，先渲染出来看。**
> 一条读起来很确定的断言，也可能建立在错误的几何假设上。
> 测试替代码说谎，比测试漏检更难发现。

## 7.20 对旧管线 PDF 的端到端比对（差分 oracle 落地）

早先 `DifferentialOracle` 只比对两份 **LightPlot 自己生成的** digest 文本 ——
那等于自己跟自己比。真正的参考答案是旧管线已经交付出去的三份 PDF。

### `lpx verify-old <rig.yaml> <old-out-dir>`

读 `out/LX_plan*.pdf` 的**文字层**（不渲染像素），抽出硬事实：

| 事实 | 来源 |
|---|---|
| 页面 841×594mm | PDF mediaBox |
| `TOTAL 32 INSTRUMENTS` | 地图签 |
| `SCALE 1:25 @ A1` | 图签比例格 |
| 每台灯的色片 | 灯号与色片两个文字对象的**空间最近邻** |

任一不符 → 退出码 2，可直接当门禁用。

### 抽取过程踩的两个坑

**坑一：PDFKit 的行序不是阅读顺序。**
`PDFKit.page.string` 按内容流原序拼行。实测里 `L201` 的下一行是另一个 `L201`
而不是它下面的灯号 —— "相邻两行即配对"这条在 PyMuPDF 上成立，换到 PDFKit 完全不成立。
修法：逐行取 selection、用 bounds 按 (y 降序, x 升序) 重排。

**坑二：重排之后仍不能靠相邻行配对。**
同一竖列有多台灯，排序会把某台的色片排到另一台灯号旁边
（实测 `503` 配到 `L156`）。修法：对每个三位灯号找**空间最近**的色片标签，
超过 30mm 不算。标注块是紧排的一组，灯与灯之间至少隔几十毫米，这个判据稳定。

### 结果

```
LX_plan.pdf          page ✓  total 32 ✓  scale ✓  30 lantern gels ✓
LX_plan_kitchen.pdf  ...                          30 lantern gels ✓ in scene 'kitchen'
LX_plan_boston.pdf   ...                          30 lantern gels ✓ in scene 'boston'
result: identical on every checked fact
```

### 为什么是 30 组而不是 32

旧管线在 BOOM 杆上把同色片的三台灯**共用一个色片标注**
（右侧只有一处 `L156`，601/602/603 都用它）。
那不是缺失 —— 是旧图的排版方式。30 个标注位已覆盖全部 32 台灯的色片信息。

### 场景必须用场景状态去比

旧图 `LX_plan_kitchen.pdf` 印的是 `gel_override` 替换后的色片（L132→L202）。
拿基础文档去比会全线报错 —— 那不是缺陷，是比错了对象。
`OldPipelineCheck.run(states:)` 按文件名对应的场景逐个比对。

有一条测试专门钉住这点：**用不带状态的调用去比场景图必须失败**。
否则"比对通过"可能只是碰巧一致，而不是真的读取了替换规则。

## 7.21 对旧管线 DXF 的几何回归 + 一键脚本

### DXF 能证明坐标，PDF 只能证明标注

`out/LX_plan.dxf` 里每台灯是一个 `INSERT`（块引用），插入点就是它在
图纸上的确切位置。39 个 `SYM_*` 实体中 32 个落在平面区（x<690mm），
其余 7 个是图例示例符号 —— 灯号由相邻的 `LBL_*` 块按最近距离绑定，
实测配对距离 8.3–15.0mm，无歧义。

表已冻结成 Swift 常量（32 行），所以旧管线即使被删也不影响回归。

### 比什么、不比什么

| 比 | 不比 |
|---|---|
| 每台灯的世界坐标（Resolver 独立重算 vs DXF） | 绝对图纸坐标（图框原点**故意**不同） |
| 同类型灯的间距 = 世界间距 ÷ 25（**69 对全部零误差**） | |
| 横杆灯的 x 映射是纯平移（散布 < 0.001mm，原点 355.0） | |
| 每台灯的灯具类型 | |

### 反解出来的一个真实差异

竖杆（BOOM）上的灯，旧管线沿**半个管粗**（0.9738mm 图纸 = 24.3mm 实物）
向台中心偏移 —— 物理上灯是夹在管侧面的。LightPlot 放在管轴线上。

这条差异没有躲着，而是被**量了出来**并写进测试
（`boomOffsetIsMeasured`）：数值、方向、左右镜像全部钉死。
将来若有人改动这条约定，会立刻知道改掉的是什么。

### 剖面图回归

旧剖面图的 `TRIM SCHEDULE`（7 个构件 × trim × 类型）逐行核对，
全部一致。同时用测试守住"剖面必须比旧管线更复杂"这条产品要求：

| 项 | 旧图 | LightPlot |
|---|---|---|
| 构件表 7 行 | ✓ | ✓ |
| 每排灯具计数 | — | ✓（`x8` / `x4`） |
| 光束射程 | — | ✓（1737 / 4830 / 5715 / 5739） |
| 视线分析 | — | ✓（6 of 7 rows blocked, worst −118mm） |
| 虚线标"切面之外" | — | ✓ |
| 楼梯 / 台上实物 | — | ✓（STAIR +2400） |

### `./run.sh` —— 一条命令出全套

用户是文科生，不能让他记十条命令。所以 `app/run.sh`：

```
[1/5] 编译
[2/5] 数据校验（硬门禁，有错不出图）
[3/5] 出图（6 份 PDF + 6 份 CSV）
[4/5] 与旧管线比对（逐灯核对色片）
[5/5] 小结
```

三种模式：默认全跑、`--check` 只校验、`--verify` 只比对。
退出码：0 全绿 / 1 数据或环境错 / 2 与旧管线不一致。

### `lint` 与 `render` 曾对同一份数据给出不同判断

`render` 会先从内建库补全色片颜色，`lint` 不会。
于是 `--strict` 把"色片表没写色值"报成 8 条警告并拒绝出图 ——
而那 8 个色值根本不需要用户提供（库里就有）。

**门禁挡住的其实不是问题，这种失败最消耗信任。** 修法：`lint` 也补全。

## 7.22 应用/CLI 逐字节一致、纸张扫描、文字避让

### 应用与命令行必须是同一个程序

GUI 和 `lpx` 是同一核心的两个外壳。若它们对同一份数据产出不同的图，
用户看到的东西和他交付的东西就不是一回事 —— 这类缺陷最难发现，
因为两边各自"看起来都对"。

`AppMatchesCLITests` 用**逐字节比较**：两边都写 PDF，正规化后 `Data` 必须相同。

正规化是必要的：CoreGraphics 会在 PDF 里写 `/CreationDate`、`/ModDate`
与 `/ID`（规范要求唯一）。这些是**文档属性，不是图面内容**。

> 早先 `PROGRESS.md` 写着"PDF 字节级可复现（cmp 验证）"—— 那是**碰巧**：
> 两次运行落在同一秒里，时间戳相同。真正验证之后才发现，跨进程必不相同。

新增 `PDFReproducible` + `lpx --reproducible`，让可复现成为**真功能**：
改一盏灯、再出图、`cmp` 一下就知道图有没有变。

### 顺带修掉一个死代码

`SheetPDF` 里构造了元数据字典却赋给 `_`，从未进入 PDF ——
打开文件属性是空的，看起来像没做完的工具。改为在建上下文时传入
`auxiliaryInfo`。

### 纸张扫描揭出七类版面缺陷

`PaperSweepRealDataTests` 扫 **7 种幅面 × 2 朝向 × 5 个比例 × 真实数据**，
判据是硬的：装得下就必须零重叠、纯 ASCII、全部落在纸内、比例说真话；
装不下就必须出提示页并点名是哪张纸。

一次扫出：

| 缺陷 | 根因 |
|---|---|
| 图签写 `1:25 @ A1` | 第三个硬编码比例（前两个在说明栏与剖面副标题） |
| A2/A3 图例压说明栏 | `notesBandHeight = 46` 是错的，实际占 62mm |
| A4/Letter 图例高度为负 | 图签固定 126mm + 说明 66mm > 可用 170mm |
| A3 纵向说明文字伸出图框 | 未限宽，压住分区字母 |
| 图例类型行压计数 | 窄栏（41mm）里 "FOLLOW" 就有 13mm |
| 图例色片名伸出图框 | "L132 Lee 132 Quarter CT Straw" 有 50mm |
| 分区数字画进图签区 | 平面图与剖面图都有 |

**`notesBandHeight = 46` 是最坏的一类错误：偶然正确。**
A1 上因为 `top − 190` 比它大，图例被推到更上方，碰巧避开了；
A2/A3 上 `top − 190` 更小，图例就从 46 起，直接压在说明上。
**偶然避开比明显出错更坏 —— 它让错误的常数看起来是对的。**

### 新增：文字避让器（`TextFitter`）

图纸"装得下"不等于"读得出来"。1:100 时图缩小 4 倍而字号不变，
32 台灯的标注必然叠成一团。

`TextFitter` 按优先级逐步丢弃重叠的文字，并**如实报告丢了多少**：

| 层 | 丢了会怎样 |
|---|---|
| 图签 / 说明 / 图框 / 图例 | 不可丢 |
| 色片号 / 灯号 | 丢了要在图上印警示横幅 |
| 通道号 | 同上 |
| 标高 | 可丢（剖面图的构件表里有完整一份） |
| 光区名 / 布景名 | 可丢（边界与形状还在） |

**色片号必须比标高优先。** 早先 DIM 排在 FIXTURE_TXT 之上，
两者相撞时被丢掉的是色片（实测 A1@1:50 的 `L119`）——
丢色片是执行错误，装片的人会装错。

实测结果：

| 比例 | 结果 |
|---|---|
| 1:25 | 零丢弃 |
| 1:50 | 色片全部保留，只让 1 个标高退让 |
| 1:100 | 标注放不下 → 图上印 `LABELS OMITTED: N ... Use a larger scale` |

### iPad target 曾经悄悄坏掉

加场景 UI 时，`EditorView` 的 iOS 分支缺 `exportSchedules` /
`exportAllStates` 两个函数，target 编译失败。

新增 `tools/platforms.sh`：macOS Debug、macOS Release、iPadOS 三个
target 必须都能编译，并接进 `run.sh` 的第 5 步。
iPad 的**观感**仍需真机验证，但"编译不过"这种低级破坏从此有门禁。

## 7.23 换一部戏 / 极端数据

### 换项目是产品承诺，得真的验一次

`SecondShowTests` 用一部**处处不同**的戏（Dürrenmatt《The Visit》）
走完整条链路：9×6m 舞台、5 个构件、12 台灯、5 个色片、两个新场景。
代码一行不动，只换数据。

它立刻抓到四个真问题：

| 缺陷 | 根因 |
|---|---|
| 色片表必填 `purpose` | 描述性字段被当成必需，手写 YAML 直接 `keyNotFound` |
| 解码时自动补 `rgb` | **解码不得改动文档**（三条往返测试立刻抓到） |
| 通道号被丢 | 构件名优先级高于通道号；而通道号只出现在图上这一处 |
| 幕次标签消失 | 见下 |

### 幕次标签一直被静默丢弃

真实 `scenes.yaml` 把幕次写在 `id:` 里：

```yaml
scenes:
  kitchen:
    id: ACT 1        # ← 这是幕次，不是 id
    name: KITCHEN / NIGHT
```

而场景的 id 来自**字典键**（`kitchen`）。代码里 `s.id = key`
把 `id: ACT 1` 覆盖掉了 —— 于是 `act` 永远是空串，
场景横幅上一直只显示场景名，从没显示过"第几幕"。

修法：`act` 缺省时用文件里的 `id` 顶上。
现在横幅读作 `ACT 1  KITCHEN / NIGHT`，与数据作者的意图一致。

同一处还有第二个 bug：`LightingState` 强制要求 `id` 存在，
于是按文档"键即 id"手写的 scenes.yaml 必然报 `keyNotFound`，
而错误信息完全指不出问题在哪。现在 `id` 可缺省。

### `gel: nil` 与 `gel: OPEN` 曾经说三种话

同一份数据：平面图画 `-`、CSV 里是空串、图例却列 `OPEN`。
读图的人只能猜。

新增 `Fixture.gelCode`：`nil` 与 `OPEN` 是同一件事（没装色片），
五处调用点统一走这一个入口。

### 极端数据

`ExtremeDataTests`（9 条）覆盖：空文档、1cm 到 60m 的舞台、
1 台灯、100 台灯、缺色片/缺通道/缺角度的灯、
挂在不存在构件上的灯、6 种比例 × 全部纸张、非法比例。

判据是硬的：**要么画出内容，要么明说装不下 —— 不许空白、不许崩。**
非法比例（0 或负数）必须被 `SheetLayout.isValid` 挡下，
绝不允许 NaN/inf 坐标流进 PDF。

## 7.24 交互压力与应用内完整流程

### 压出两个真 bug

**一、拖动杆端可以把两端拖交叉。**
早先直接赋值，把起点拖过终点就得到 `x0 > x1` 的倒置杆 ——
桁架几何、长度、吸附全部失去意义，而图上"看起来还是一根线"。

现在拖到另一端时**停在最短长度（100mm）**，不翻转也不倒置。
没选"自动交换两端"：那会让用户失去对"哪端是 start"的控制，
而吸附与灯具轴坐标都依赖这一点。

**二、撤销栈只有 200 步。**
一次真实的设计会话有几百次操作，用户会发现"想撤回半小时前"已经撤不动。
提到 1000 步（每步约 3–8KB 文档快照，总共约 8MB），换一整个工作日的历史。

顺带确认了一条正确行为：**设成相同值不压栈**。
300 个事件里只有 250 个产生撤销点 —— 否则用户按撤销会"按很多次什么都没变"。

### 应用内完整流程

`AppWorkflowTests` 按用户真实顺序走一遍，每一步都经过**真实视图代码**：

```
打开真实项目 → 画布出指令（>500 条、5 个必需图层）
  → 点选灯具（视图坐标 → 图纸坐标 → 命中测试）
  → 检查器改色片/通道 → 沿杆拖动
  → 切 kitchen / boston / 回基础图
  → 换 A0 → 回 A1 → 导出 PDF + CSV
  → 存 .lpx → 重开 → 编辑仍在
  → 用 PDFKit 读回导出文件量尺寸（841×594 / 420×297）
```

还有三条独立的：每一步都能撤销回原点、脏标记正确、
剖面页可达且含 TRIM SCHEDULE 与 SIGHTLINE。

**测试里踩到的一个坑值得记下**：视图坐标变换必须用**模型自己的**
`toView` / `paperPoint` 一对。我一开始用 `state.viewport.toView()`
手算，而 `paperPoint` 用的是模型的自动适配视口 —— 两者不是同一个，
于是"点哪儿都点不到"。这不是产品缺陷，但说明**测试也得走真实的变换路径**。

## 7.25 界面验收：两个真实可用性缺陷

用 `NSHostingView` 把**真实的 `EditorView`** 离屏渲染成图（`AppLookTests`），
相当于在无显示环境里看了一眼应用。两个缺陷立刻现形：

### 一、检查器默认是关的

初学用户打开应用，看到一张图纸加几个图标 —— 改剧名、改场地、
改灯具的地方**全都藏在一个按钮后面**。整个应用看起来像看图器，不像编辑器。

对非技术用户，"默认可见"比"界面干净"重要得多。改为默认打开。

### 二、浮层工具栏压住图纸顶部

`canvasH = geo.size.height` —— 画布占满整个高度，而工具栏与状态栏是
`overlay` 浮在上面的。适配之后图纸顶部正好钻到工具栏底下，
光区名 `K2` 被完全盖住。

修法：`Viewport.fitted` 新增 `topInset` / `bottomInset`，
`EditorModel` 用 `chromeTopPoints = 56`、`chromeBottomPoints = 44`
在适配时把这段让出来。

**没有采用"统一加大 padding"**：那会连左右一起缩小，
在大窗口里白白浪费宽度。也没有把工具栏改成参与布局的 `VStack` ——
浮层是已经调好的观感，能靠算法让开就不动它。

### 顺便清掉一处测试可复现性缺陷

压力测试里用了 `SystemRandomNumberGenerator`。一次失败之后无法复现
那一串操作 —— 这类"偶发红"对信任的破坏比真 bug 还大，
它会训练人忽略失败。换成固定种子的 LCG，5 个种子各跑 200 步。

同时把断言从 `|| true`（恒真，等于没断言）改成四条真不变量：
灯号唯一、坐标有限、挂杆的灯有沿轴坐标、比例与版面合法。

## 7.26 界面在三种窗口尺寸下的验收

用 `NSHostingView` 把真实的 `EditorView` 在 **900×620 / 1280×820 / 1800×1100**
三种尺寸下渲染出来看。这一步抓到的全是"缩略图里看不出来"的问题。

### 工具栏在最小窗口下被裁

900pt 宽时，12pt 间距的按钮总宽超过窗口，最右边的**导出**按钮
直接被裁掉 —— 用户根本点不到。

改成 `ViewThatFits` 三级降级：常规间距 → 紧凑间距 → 横向可滚动。
任何宽度下所有按钮都够得着。

### 工具栏盖住检查器顶部的场景选择器

工具栏是浮在画布之上的，窗口不够宽时横跨到检查器上方。
实测 900pt 时，检查器最顶部的"场景"选择器被整块盖住 ——
而切换场景是主要操作之一。

修法：检查器顶部让出浮层高度（`chromeTopPoints = 56`）。

**没有用"先判断会不会重叠"再决定**：那个判断依赖工具栏的实测宽度，
而它会随字体、语言、系统版本变化。无条件留一条固定间距，
宽窗口下看起来就是正常留白 —— 简单且不会错。

### 中途试过、又退回来的方案

曾把"并排显示检查器"的阈值从 900 提到 1024，想让窄窗口走覆盖模式。
看图之后发现更糟：覆盖模式反过来让**工具栏右侧被检查器盖住**，
"场景"和"导出"都点不到了。退回来，改用预留间距。

> 教训：Z 序冲突这类问题，看图之前不要凭推理拍板 ——
> 两个方向都"有道理"，实际观感差别很大。

### 剖面页的状态栏比例错了

状态栏直接读 `state.layout.scaleDenominator`（平面图的 1:25），
在剖面页上仍显示 1:25，而那张纸实际是 1:50。
读图的人会拿这个数字量距离，所以它必须跟着页面走。
新增 `currentScaleDenominator`，按 `page` 取值。

### 派生视口漏了内缩

`fitToSheet()` 已经会用内缩让开浮层，但**派生视口**（用户还没手动
接管视角时每次重算的那个）没有 —— 于是初始视角仍会把图纸顶到工具栏底下。
两处现在用同一组内缩，`ChromeLayoutTests`（3 条）同时锁住两者。

## 7.27 可达性审计：实现了但用户碰不到 = 没实现

把 `EditorEvent` 的 27 个编辑动作与界面逐个对照，发现 `setOrigin`
**只有测试在用**：检查器里只有一个"居中"按钮，想整体挪开 5mm 没有任何办法。

而"比例锁死、只移动图框"本来就是这套版面的设计原则 ——
位置理应是可调的。补上检查器里的"在纸上微调"四个方向键（每次 5mm），
只挪图框不动比例，装不下时照样报"装不下"。

`ReachabilityTests` 直接读源码做静态检查：新增一个事件却忘了接线，
测试立刻变红。朴素，但"实现了但用户碰不到"与"没实现"对用户来说是同一件事。

同一次审计还补上了 README 里承诺过、但脚本里并不存在的 `./run.sh --app`
（编译并打开图形应用）—— **文档承诺的功能必须真的能用**。

### 光区标签贴边的钳位写错

`min(r.y1 - 3 - cap/2, safe.y1)` 在"安全区上界比光区顶边更高"时，
钳位结果正好贴在光区顶线上。正确的是**先取两个上界里更低的那个**再内缩：
`min(r.y1, safe.y1) - 3 - cap/2`。

现在数值实测标签框顶距光区顶线 3.00mm（cap 6.09mm），`ZoneLabelTests` 锁住。

> 这一条我先在缩略图里"看到"问题、改完又"看到"还在 ——
> 最后用数字确认才发现两次目视都不可靠。
> **低分辨率下不要用眼睛判定细部几何。**

## 7.28 让状态文档与现实一致

收尾审计发现 `TASKS.md` 仍写着"P0 阻塞交付"，而其中两项
（cue sheet、running script、script.yaml 真剧本）**已被用户明确取消**。
一份自称"被 P0 阻塞"的待办清单压在交付物上，是自相矛盾的。

重写之后：
- 只剩 **一项真 P0**：把示例场地换成用户自己的场地 —— 这条**只能等用户**，
  AI 无法自行获得真实尺寸。
- P1 是需要真机/真人验证的三项（1:1 打印、iPad 触感、真机签名）。
- 补上一条此前没写明的边界：**LightPlot 不导 DXF/DWG**，
  CAD 文件由旧 Python 管线生成（`out/cad/`）。
  交付要求是"打印出来量得到真实尺寸"，PDF 已满足，所以这是**边界不是缺口** ——
  但不写清楚，用户会以为应用里找不到导出按钮是 bug。

> 教训：状态文档写错和代码写错一样有害，而且更难被发现 ——
> 代码错了测试会红，文档错了没人会红。

## 7.29 界面中文化

审计到这里才注意到最影响这个用户的一件事：**整个应用界面是英文的**，
而用户是中文的文科生，"啥都不懂"。

### 为什么不用系统本地化

`LightPlotUI` 是 SwiftPM 目标，同时被 macOS 与 iPadOS 两个 Xcode 目标引用。
走 `Localizable.strings` / `.xcstrings` 需要 `defaultLocalization` + 资源包 +
工程配置三处对齐，任何一处漏掉的表现是**界面静默变回英文** ——
而测试跑在英文环境里，这种失败自动化根本看不见。

改成显式表 `L10n.table`（英文原串即键，值中文）：

- 表里没有的键**原样返回英文**，漏翻只会显示英文，不会显示成键名或空白。
- `LocalizationTests`（6 条）直接扫源码与枚举：
  1. 每个 `L10n.t("…")` 键必须在表里（缺了会指名是哪个文件用的）
  2. 遍历 `MetaField` / `StageField` 的全部 `title`，必须都有中文
     （检查器的字段名不是字面量，只扫 `L10n.t("…")` 会漏掉它们）
  3. 中文不能是空串，也不能与英文相同（那就是没翻）
  4. 源码里不许再出现 `String(localized:)`（它会静默绕过这张表）
  5. 切语言必须真的改变输出；未收录的键退化为英文
  6. 表规模与语言判定

术语处理：`trim` / `cue` / `gel` / `DMX` 保留英文 ——
中文剧场里也是直接说英文，译成"吊杆高度"反而对不上现场。

### 一个必须同时守住的边界

中文只在**界面**里。图面（PDF/DXF）仍然是纯 ASCII ——
这是项目的铁律，且由 `EventSanitizer` 在编辑入口强制。
本轮改动后重新出图复核：6 份 PDF 文字层里**一个汉字都没有**。

## 7.30 iPad 布局：能验什么、不能验什么

`LookIPadTests` 用 `NSHostingView` 在 iPad 的几种尺寸下渲染真实 `EditorView`。

### 一个差点得出假结论的地方

第一版把 834×1194（iPad 竖屏）也拿来测，渲染出来"能出图"，我就准备写"竖屏正常"。
但量了一下画布宽度：**613pt**，而窗口是 834 —— 差 221。

原因是 `EditorView` 在 macOS 上带 `.frame(minWidth: 900)`：
用 834 宽渲染时，SwiftUI 先按 900 布局，再把结果裁到 834。
所以我看到的根本不是 iPad 竖屏排版，而是**被裁掉一角的 macOS 排版**。

改成只测 ≥900 宽的尺寸（iPad 横向四种），并断言画布宽度 > 600 ——
这样"能出图"就不再是唯一判据，**尺寸本身**也被检查。

竖屏排版（检查器变抽屉那条路径）只能在 iPad 模拟器或真机上看，
已写入 §8 的诚实缺口，不再假装测过。

## 7.31 打包成 .app / .dmg（以及打包过程中抓到的四个真 bug）

`package.sh` 一条命令出 `.app` 与 `.dmg`，六步每步都有自检，
最后**挂上镜像真的启动一次**才算成功 —— 静态检查证明不了"能用"。

打包过程本身抓出四个问题，全部是真缺陷：

### 一、双击 .lpx 根本没打开文件

`project.yml` 把 `.lpx` / `.yaml` / `.json` 声明成本应用可打开的类型，
于是 macOS 会让我们成为这些文件的默认打开方式。但应用**没有任何接收器** ——
双击只会启动应用、停在示例文档上。那比不声明更糟：用户会以为图纸坏了。

补上 `DocumentOpenRelay`（放在可测试的 UI 层），并处理一个时序坑：
`application(_:open:)` 可能在窗口就绪**之前**触发，所以先缓冲、就绪后再交付。
早到/晚到两种时序都有测试（`DocumentOpeningTests`，4 条）。

### 二、PDF 里版本号永远是 0.1.0

`LightPlotVersion.string` 是写死的常量，应用 bundle 里的 `MARKETING_VERSION`
根本没被读过。改成优先读 bundle、命令行退回常量。

### 三、`/ModDate` 从未被正规化（可复现性其实一直是坏的）

`PDFReproducible` 按**行**找 `/ModDate (D:`，而 CoreGraphics 会把它和值
拆到两行：

```
/CreationDate (D:…) /ModDate
(D:2026…)
```

于是 `/ModDate` 一直带着真实时钟。**"同一份数据两次出图逐字节相同"这条
此前是碰巧成立的**（两次落在同一秒内）。

这个 bug 是靠 `AppMatchesCLITests` 偶发失败（约 1/6）暴露的 ——
一个 33127 字节的 PDF 里只差 1 个字节（秒数的 '5' 与 '6'）。
单跑该测试 10 次全绿，只有全量并行时偶发 ——
说明"偶发红"确实值得追，它后面往往藏着真缺陷。

### 四、固定日期带了双重的 `D:` 前缀

`fixedDate` 自带 `"D:"`，而键里已经含 `"(D:"` —— 替换后得到 `(D:D:2000…)`。
PDF 阅读器照样能读，肉眼也看不出来，所以一直没人发现。

修法：**整段替换括号里的值**，而不是在 `(D:` 之后拼接。
新测试直接喂 CoreGraphics 的真实排版（跨行的 `/ModDate`），
断言不出现 `D:D:`、两个日期都变成同一个固定值。

### 五、应用没有图标

打包出来是通用图标。对一个"成品交付"来说这是明显缺口 ——
用户是靠图标认应用的。生成了一套 10 个尺寸的图标
（桁架 + 两盏灯 + 渐隐光束 + 落点地面线），32px 下仍能认出是什么。

## 8. 已知的诚实缺口

> 这一节只写**现在仍然成立**的缺口。已经做到的不要再留在"缺口"里 ——
> 那会让人误判项目状态（本节曾长期写着"字体没内置""色片没真实颜色"
> "剖面图没做""iPad UI 没写"，全部早已不成立，已删除）。

**能力边界（刻意不做）**

- **不算照度。** 光束锥只表示朝向与光斑宽度。真算照度需要光度曲线与环境反射，
  图纸里没有这些数据 —— 画一个好看的假光斑比不画更糟。
- **不导 DXF / DWG。** LightPlot 出 PDF 与 CSV；CAD 文件由旧 Python 管线生成
  （`out/cad/`）。交付要求是"打印出来量得到真实尺寸"，PDF 已满足（实测 841×594mm）。

**需要外部条件才能验证的**

- **示例场地是虚构的。** `data/rig.yaml` 里 15×9m 的"黑箱剧场"不是真场地。
  换成用户自己的场地需要用户提供尺寸（`TASKS.md` 唯一的真 P0）。
  在此之前，任何图都只能当"格式演示"。
- **1:1 打印未在实体打印机上验证。** 软件侧只验证了 PDF 的**逻辑**尺寸。
- **iPad 竖屏排版未验证。** `EditorView` 在 macOS 上有 `minWidth: 900`，
  离屏渲染竖屏尺寸会被裁剪，看到的不是 iPad 真实排版 ——
  必须在 iPad 模拟器或真机上看。横向四种尺寸已验（`LookIPadTests`）。
- **iPad 触感未验证。** Pencil 延迟、捏合跟手程度只有上手才能判断。
- **iPad 真机 Release 签名**需要用户自己的 Apple 开发者团队；模拟器构建不需要。

**数据完整性**

- **色片库覆盖 Lee / Rosco 常见色号**（`GelLibrary`）。未收录的色号不会瞎猜颜色 ——
  图例画空心框并在 `lint` 里报 `gelMissingColor`，这是**故意可见**的缺口。
